# AGENTS.md

Поведенческие правила для сокращения типичных ошибок LLM при работе с кодом. При необходимости объединяйте с инструкциями конкретного проекта.

**Компромисс:** эти правила смещают баланс в сторону осторожности, а не скорости. Для тривиальных задач руководствуйтесь здравым смыслом.

## 1. Думай, прежде чем писать код

**Не делайте предположений. Не скрывайте непонимание. Озвучивайте компромиссы.**

Перед реализацией:
- Явно формулируйте свои предположения. Если сомневаетесь — спрашивайте.
- Если возможны несколько трактовок, представьте их все — не выбирайте молча.
- Если есть более простое решение, скажите об этом. Возражайте, когда это оправдано.
- Если что-то непонятно, остановитесь. Назовите, что именно вызывает вопросы. Спросите.

## 2. Сначала простота

**Минимум кода, решающего задачу. Ничего спекулятивного.**

- Никаких функций сверх того, что было запрошено.
- Никаких абстракций для одноразового кода.
- Никакой «гибкости» и «настраиваемости», о которых не просили.
- Никакой обработки ошибок для невозможных сценариев.
- Если вы написали 200 строк, хотя хватило бы 50, — перепишите.

Задайте себе вопрос: «Сказал бы опытный инженер, что это переусложнено?» Если да — упрощайте.

## 3. Хирургические изменения

**Затрагивайте только то, что необходимо. Убирайте только собственный мусор.**

При редактировании существующего кода:
- Не «улучшайте» соседний код, комментарии или форматирование.
- Не рефакторьте то, что не сломано.
- Придерживайтесь существующего стиля, даже если сделали бы иначе.
- Если заметили несвязанный мёртвый код, упомяните его — не удаляйте.

Когда ваши изменения порождают «осиротевшие» элементы:
- Удаляйте импорты/переменные/функции, которые стали неиспользуемыми именно из-за ваших изменений.
- Не удаляйте мёртвый код, существовавший ранее, если об этом не просили.

Проверка: каждая изменённая строка должна напрямую вытекать из запроса пользователя.

## 4. Работа от цели

**Определите критерии успеха. Итерируйте, пока не убедитесь в результате.**

Превращайте задачи в проверяемые цели:
- «Добавить валидацию» → «Написать тесты на некорректные данные, затем добиться их прохождения»
- «Исправить баг» → «Написать тест, воспроизводящий баг, затем добиться его прохождения»
- «Отрефакторить X» → «Убедиться, что тесты проходят до и после»

Для многошаговых задач кратко изложите план:
```
1. [Шаг] → проверка: [критерий]
2. [Шаг] → проверка: [критерий]
3. [Шаг] → проверка: [критерий]
```

Сильные критерии успеха позволяют работать автономно. Слабые («заставить это работать») требуют постоянных уточнений.

---

**Правила работают, если:** в диффах меньше ненужных изменений, меньше переписываний из-за переусложнения, а уточняющие вопросы задаются до реализации, а не после ошибок.

### Gates

Три обязательные проверки (fmt, clippy, test) перед завершением любой работы с кодом. См. `docs/agents/gates.md`.

### Ветки, коммиты и релизы

Работа в ветках от `main` (прямые коммиты запрещены), Conventional Commits, CHANGELOG через `git-cliff`, теги без префикса. См. `docs/agents/git-workflow.md`.

### Code style

Человеческий текст на русском, `///`-контракты у публичного API, никаких магических чисел, формат через `cargo fmt`. См. `docs/agents/code-style.md`.

### Архитектура

Слои workspace, поток кадра, машина Гирлянды и OTA-конвейер описаны в `docs/agents/architecture.md`. Читай при изменении границ крейтов, добавлении Аддона и любой работе с OTA или Реестром эффектов.
